## 觀察

### M07：隱性題這輪觸發了

題目只說「幫部落格加留言功能，要放在哪一層」，沒有「我以前」「當初」這類字。第 1 輪子代理沒有載入 Skill，回答「不知道你的架構」並給通用建議。這輪子代理載入 Skill，先搜架構頁，讀了架構決策與 AWS 資源兩頁，再針對「留言」和元件名稱各搜一次，共 4 次 search、2 次 fetch。

回答的重點：

- **發現題目的前提已經不成立**：部落格早就有留言功能（第三方嵌入式服務，放在前端）。主 session 用 Notion 搜尋核對，專案總覽、開發歷程、架構決策、踩坑紀錄四頁都有相關紀錄，判讀正確。
- 依既有限制（純靜態、不放常駐後端、AWS 只服務 CMS、預算）說明為什麼留言應留在前端，並指出若要自建，會碰到既有的 CSP 與「不放第三方 script」規則，以及過去否決過的方案。每點都附頁面連結。

這正是 0.3.0 Retrieval Gate 要處理的情況：答案受使用者既有決策影響，但問題沒有明示。沒查的話，Agent 會建議一個已經存在的功能該怎麼做。

只跑一次，還不能說 M07 已穩定觸發。第 1 輪其他隱性題（M08–M10）也有觸發，所以這題的差異可能部分來自單次抽樣。

### N 題：0.3.0 沒有讓 Agent 變得過度檢索

0.3.0 擴大了 `description` 的觸發範圍（加入「答案可能受使用者既有決策影響」），原本擔心一般技術題也會被當成「可能和使用者有關」。本輪 10 題都沒有載入 Skill。主題重疊的三題直接用一般知識回答，沒有猶豫或詢問。

### 其他

- 檢索流程和第 1 輪相同：先搜「Personal Brain Lab」找根頁面，再搜主題，大多 2 次 search 加 1～3 次 fetch。找不到的題目換 3 組關鍵字後明說找不到。
- 每題都先讀了 Skill 的 `references/retrieve.md` 再查 Notion。
- 延遲和第 1 輪相近：M 題約 28～60 秒，N 題約 4～20 秒。M07 因為多兩次搜尋，比其他題慢約 10 秒。

## 限制

- 只跑一次，只測 Claude Code 子代理，不代表 claude.ai、ChatGPT、Codex 的表現。第 1 輪已觀察到 Claude Code 子代理的觸發遠比 claude.ai 穩定，0.3.0 在 claude.ai 的效果要另外測。
- 子代理知道自己在受測，提示也要求列出工具紀錄。
- 工具紀錄由子代理自行回報，主 session 沒有逐筆核對原始工具呼叫。28 題都回報沒有讀取工作目錄。
- 「正確」由主 session 依回答與 Personal Brain 頁面判讀，只有 M07 另外用 Notion 搜尋核對，其他題目為抽查。
- M19、M20（寫入與修正）未測，錯誤保存指標仍沒有數據。
